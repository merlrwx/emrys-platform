# Emrys Platform

Emrys Platform is an AKS platform built with Terraform and Flux. It provisions Azure infrastructure, installs Kubernetes platform components, and generates customer n8n environments from code.

The repository is intentionally self-contained: the Terraform roots, reusable onboarding module, Flux manifests, monitoring configuration and operational notes all live together so the platform can be reviewed as one system.


## What It Builds

- Azure Kubernetes Service clusters for staging and production
- Flux GitOps reconciliation from this repository
- Traefik ingress, cert-manager, CNPG, CNPG Barman Cloud plugin and kube-prometheus-stack
- Azure Key Vault integration through the Secrets Store CSI driver
- PostgreSQL clusters with scheduled backups to Azure Blob Storage
- Customer n8n deployments with restricted pod security, resource controls, probes and network policy
- Grafana alerting for application, database, node and pod health


## Architecture

Terraform owns the Azure layer and the Flux bootstrap. Flux owns the in-cluster desired state.

```text
Terraform
  -> resource group
  -> AKS cluster and node pools
  -> Key Vault
  -> backup storage
  -> Flux extension and kustomizations

Flux
  -> infrastructure controllers
  -> infrastructure configuration
  -> CNPG backup plugin
  -> customer applications
  -> monitoring stack
```

Customer environments are generated by Terraform into the GitOps tree. Flux then reconciles those generated manifests into the cluster.


## Repository Layout

- `staging/` is the staging Terraform root.
- `production/` is the production Terraform root.
- `modules/customer-onboarding/` generates customer Azure resources and Kubernetes manifests.
- `gitops/` contains the Kubernetes manifests reconciled by Flux.
- `docs/` contains runbooks and design notes.


## Design Choices

The platform keeps infrastructure and GitOps manifests in one repository because the cluster, controllers and workloads have ordering dependencies. For example, customer databases depend on the CNPG Barman Cloud plugin, the plugin depends on cert-manager, and monitoring depends on the workloads and controllers it observes.

Staging and production are separate Terraform roots. That keeps environment drift visible and makes each cluster independently deployable, while still allowing the two roots to share the customer onboarding module.

Customer manifests are generated instead of hand-written. A customer name in `customers.tf` becomes a namespace, database, backup configuration, secrets mapping, n8n deployment, service, ingress and network policy. This keeps repeated customer infrastructure consistent without adding a larger control plane.

Secrets stay in Azure Key Vault. Kubernetes workloads receive them through SecretProviderClass resources, which keeps secret values out of Git while still allowing Flux to manage the shape of the workloads.


## Deployment

Register the Azure Kubernetes Configuration provider and authenticate:

```bash
az provider register --namespace Microsoft.KubernetesConfiguration
az login
```

Create a Flux deploy key:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/emrys-flux -N "" -C "emrys-flux-deploy-key"
gh repo deploy-key add ~/.ssh/emrys-flux.pub \
  --repo merlrwx/emrys-platform \
  --title "emrys-flux-deploy-key" \
  --allow-write
```

Create environment tfvars files:

```bash
cp staging/terraform.tfvars.example staging/terraform.tfvars
cp production/terraform.tfvars.example production/terraform.tfvars
```

Required values include:

- `subscription_id`
- `admin_group_object_ids`
- `gitops_repo_path`
- `flux_ssh_private_key_path`

Deploy staging:

```bash
cd staging
terraform init
terraform plan
terraform apply
```

Deploy production from `production/` when ready.

## Customer Onboarding

Add customers in the environment's `customers.tf`:

```hcl
locals {
  customers = toset([
    "nimue",
  ])
}
```

Run `terraform apply` from the same environment directory. Terraform writes the generated manifests to:

```text
gitops/apps/<environment>/<customer>/
```

For each customer, the module creates:

- a dedicated namespace
- database credentials in Key Vault
- a scoped backup storage container and SAS token
- SecretProviderClass mappings for Key Vault CSI
- a CNPG PostgreSQL cluster
- a Barman ObjectStore and scheduled backup
- an n8n ConfigMap, Deployment, PVC, Service and Ingress
- a CiliumNetworkPolicy
- a customer kustomization

Customer names must be lowercase, start with a letter, and contain only lowercase letters, numbers and hyphens.


## Customer Runtime

Each customer gets an isolated n8n runtime backed by PostgreSQL.

The generated n8n configuration points at the customer's CNPG read-write service and pulls database credentials from Key Vault-backed Kubernetes secrets. Ingress hosts follow the environment domain configured in `customers.tf`, using the pattern:

```text
<customer>.<domain>
```

The generated ingress uses Traefik and cert-manager with the `letsencrypt-prod` ClusterIssuer.


## GitOps Ordering

Flux reconciles the platform in layers:

```text
infra-controllers
  -> infra-configs
  -> cnpg-plugin
  -> apps
  -> monitoring-controllers
  -> monitoring-configs
```

The order matters during a fresh cluster deployment:

- cert-manager needs to exist before the CNPG Barman Cloud plugin creates webhook certificates.
- customer databases need the Barman Cloud plugin before backup-enabled CNPG clusters can become healthy.
- monitoring is applied after applications so alerting rules can target the expected workloads.

The AKS Flux extension also waits for the user node pool. The system pool is tainted for critical add-ons, so Flux controllers need schedulable user nodes.


## AKS Hardening

The AKS configuration follows Microsoft's AKS guidance for identity, node pool separation, upgrade windows and network policy.

The cluster uses Entra ID authentication with Kubernetes RBAC. Entra ID handles authentication to the cluster, while Kubernetes RBAC remains the authorization layer inside Kubernetes.

There are separate system and user node pools:

- the system pool is tainted with `CriticalAddonsOnly` and is reserved for cluster-critical components
- the user pool runs Flux, Traefik, CNPG, monitoring and customer workloads

Automatic patch upgrades and NodeImage upgrades run during configured maintenance windows. Patch upgrades keep the cluster current within the selected Kubernetes minor version, while NodeImage upgrades keep node OS images patched.

The cluster uses Cilium for network policy and the network data plane.

References:

- [AKS Best Practices](https://learn.microsoft.com/en-us/azure/aks/best-practices)
- [AKS Architecture Best Practices](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-kubernetes-service)


## Workload Security

Generated customer namespaces enforce the Kubernetes `restricted` Pod Security Standard:

```yaml
labels:
  pod-security.kubernetes.io/enforce: restricted
```

Generated n8n pods run as a non-root user with `RuntimeDefault` seccomp, no privilege escalation, a read-only root filesystem and all Linux capabilities dropped.

Writable paths are explicit:

| Path | Purpose |
|------|---------|
| `/tmp` | temporary files and workflow scratch space |
| `/home/node/.cache` | application cache |
| `/home/node/.n8n` | persistent n8n data |

The first two paths use `emptyDir` volumes. Persistent n8n data uses a PVC.

Resource requests and limits are set by module variables, with defaults of `256Mi` and `100m` for requests and `1Gi` and `1000m` for limits. Liveness and readiness probes use the n8n `/healthz` endpoint on port `3008`.


## Network Policy

Customer n8n pods are restricted by CiliumNetworkPolicy.

Allowed ingress:

- Traefik to n8n on port `3008`

Allowed egress:

- the customer's CNPG database on port `5432`
- kube-dns on port `53/UDP`
- external HTTPS on port `443` for webhooks and integrations


## PostgreSQL Backups

CNPG uses the Barman Cloud plugin to store base backups and WAL files in Azure Blob Storage. Each customer has its own backup storage path and SAS token.

Scheduled backups are defined with CNPG `ScheduledBackup` resources. Manual backup checks can be run with:

```bash
k cnpg backup <cluster-name> --method=plugin --plugin-name=barman-cloud.cloudnative-pg.io
k describe scheduledbackups.postgresql.cnpg.io <scheduled-backup-name>
```

The generated CNPG cluster manifests include commented recovery configuration for point-in-time recovery work.


## Monitoring

Monitoring is deployed with kube-prometheus-stack. Alertmanager is disabled and Grafana native alerting is used instead.

The monitoring stack is split into:

- `monitoring-controllers` for kube-prometheus-stack
- `monitoring-configs` for Grafana alert rules, contact points and notification policy

Grafana loads alert definitions from ConfigMaps labeled with `grafana_alert: "1"`.

Current alert coverage includes:

- n8n availability
- CNPG operator availability
- Barman Cloud plugin availability
- backup failures
- WAL archiving failures
- replication lag
- database fencing
- node readiness
- filesystem pressure
- pending or unknown pods

Grafana admin credentials and Telegram credentials are stored in Key Vault. Terraform creates placeholder Telegram values with `ignore_changes`, so real values can be set directly in Key Vault without being overwritten on later applies.

```bash
az keyvault secret set \
  --vault-name "kv-emrys-staging" \
  --name "grafana-telegram-bot-token" \
  --value "$BOT_TOKEN"

az keyvault secret set \
  --vault-name "kv-emrys-staging" \
  --name "grafana-telegram-chat-id" \
  --value "$CHAT_ID"
```

Retrieve the Grafana password:

```bash
terraform output -raw grafana_admin_password

az keyvault secret show \
  --vault-name kv-emrys-staging \
  --name grafana-admin-password \
  --query value \
  -o tsv
```


## Alert Testing

Suspend Flux before deliberately breaking a workload:

```bash
flux suspend kustomization --all
```

Trigger an n8n availability alert:

```bash
kubectl scale deployment nimue-n8n -n nimue --replicas=0
kubectl scale deployment nimue-n8n -n nimue --replicas=1
```

Trigger a CNPG operator alert:

```bash
kubectl -n cnpg-system scale deployment cnpg-system-cnpg-cloudnative-pg --replicas=0
kubectl -n cnpg-system scale deployment cnpg-system-cnpg-cloudnative-pg --replicas=1
```

Resume Flux afterwards:

```bash
flux resume kustomization --all
```


## AKS Identity Notes

Customer SecretProviderClass resources are generated with the current AKS Key Vault Secrets Provider identity.

The Grafana SecretProviderClass is part of the static GitOps monitoring manifests, so it must be updated if the AKS cluster is recreated and receives a new managed identity. The Terraform output includes a reminder with the current identity value.

Update the patch in:

```text
gitops/monitoring/controllers/<environment>/kube-prometheus-stack/kustomization.yaml
```
